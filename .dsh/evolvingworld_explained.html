01概览

把小说变成一个可以"演下去"的世界——两个 LLM 分别扮演导演和演员，让角色和世界在推演中持续演化。

一句话

用两个模型分别担任 World Model（导演） 和 Character Agent（演员），从小说某个时间点开始，一场一场把故事推演下去，同时让角色档案和世界状态持久演化、互相影响。

它想解决什么

现有角色扮演 AI 有两个根本缺陷：

  1. 角色是静态的——设定一个"林黛玉"，她从头到尾都是那个林黛玉，不会因为经历了什么而改变
  2. 世界是静态的——背景设定写死在 prompt 里，角色做什么都撼动不了这个世界

论文指出前人工作的三个不足：角色扮演 agent 依赖静态人设；多智能体环境用手工沙盒难以扩展；已有书籍驱动系统只做单场景或部分长程更新。

四个贡献

① 问题重新定义

把文学世界模拟从"模仿人设"重新定义为长程共演化，目标从"复现原著"转向"维持一个自洽、持续发展的世界"。

② 框架

开放式 schema 的 Character Agent（带 hidden tracker）+ LLM World Model（全局/地点/实体级状态），拆成 7 个可训练任务。

③ 基准

57 本书、138,596 条训练样本、222 个测试快照、20 指标轨迹级评测。

④ 实证

证明能缓解长程性能衰减（BookWorld 随场景数增加而掉分，EvolvingWorld 不掉，PES 甚至上升）。

仓库结构

模块行数职责
data_construction/7,700原始书籍 → 结构化数据 → SFT 训练集 + 测试快照

关键定位

这不是"提出新模型"的论文，而是"框架 + 数据集 + 评测基准"的论文。模型用的是现成开源 LLM 做 LoRA 微调，没有新架构、没有预训练、没有 RL。数据才是主体——data_construction/ 占了 40% 代码量。

03框架

两个模块 + 一份持久状态，按场景滚动推进。

信息不对称

World Model（导演）

看：全局状态 + 所有地点状态 + 所有角色状态
管：演什么、谁演、在哪演、世界怎么变

Character Agent（演员）

看：全局状态 + 自己所在地点 + 自己完整状态（别人只有短描述）
管：我这个角色怎么演、演完变成什么样

导演能看到全图，演员只能看到自己那一格。演员不知道别人心里在想什么，除非对方说出口或做出来。

7 个任务

点击展开每个任务的输入输出。

1scene_cast导演
输入全局状态 + 所有角色短描述 + 上一场剧本和互动
输出{has_next_scene, involved_characters}
决定还有没有下一场、谁出场。返回 false 则整个仿真结束。注意：先选人，再选地方。
2location_scenario导演
输入全局状态 + 所有地点描述 + 已选角色短描述 + 上一场
输出{location, scenario}
定地点、写剧本。地点用描述而非完整实体状态，控制输入长度。
3motivation_update演员
输入自己的档案 + 隐藏追踪器 + 短描述 + 上一场 + 本场设定 + 其他角色短描述
输出{motivation}
每个出场角色各自生成"我带着什么心态进这场戏"，1–3 句。
4next_character导演
输入全局 + 本地点状态 + 剧本 + 已发生的互动
输出["角色名"] 或 ["<SCENE_END>"]
决定下一个谁动。可以是单个角色、多个角色（联合动作）、或 Environment（环境描写）。
5interaction_gen演员
输入自己的完整状态 + 本地点状态 + 剧本 + 已发生的互动（别人的内心独白被剥掉）
输出一段文本：[内心想法] 说的话 (做的动作)
生成这一轮的内容。这是唯一一个输出非 JSON 的任务。
6world_update导演
输入全局 + 本地点状态 + 剧本 + 之前的互动 + 刚发生的这一条
输出{update_global, global_state, update_location, location_state, reason}
判断这条互动有没有造成持久改变。大多数时候答案是"没有"——训练时负采样按 1:1 配平。
7character_update演员
输入自己的档案 + 隐藏追踪器 + 短描述 + 本场剧本 + 本场全部互动（只保留自己可见的部分）
输出{hidden_tracker, should_update_profile, updated_profile, description, enhanced_next_motivation}
每个出场角色更新自己。整个框架最精妙的地方——见下面的 hidden tracker。

一次场景的完整流程

① scene_cast没人了？→ 结束整个仿真
↓
② location_scenario定地点 + 写剧本
↓
③ motivation_update × N每个出场角色生成动机
↓
循环 k = 1..K④ next_character → ⑤ interaction_gen → ⑥ world_update
↓
⑦ character_update × N每个角色更新自己
↓
场景 t+1状态带着走

三个关键机制

机制 1 · 开放式 Schema

不给固定字段，每本书自己决定追踪什么维度。全语料共出现 581 个角色维度、136 个世界维度。对比 BookWorld 的固定 schema（background / personality / relationships / goals / current_state），开放式让《红楼梦》能追踪家族礼法、《三体》能追踪文明危机。

机制 2 · 隐藏追踪器（多时间尺度演化）

角色不是"经历一件事就立刻变性格"：

日常小事 ──► 只写进 H（隐藏追踪器），作为弱信号沉淀
                │
                │ 反复累积
                ▼
重大事件 ──► 阈值被突破 ──► 才写进 P（档案）

character_update 输出里有两个关键字段：

{
  "hidden_tracker": "更新后的追踪器（<300 词）",
  "should_update_profile": true / false,
  "updated_profile": "只有 true 时才写"
}

提示词明确要求：只在发生有意义的、可观察的变化时才更新档案（关系转变、改变目标的决定、改变人格的创伤）；或者隐藏追踪器累积的信号加上本场，突破了阈值。不要为轻微的、短暂的反应更新档案。

消融：去掉隐藏追踪器，PUF 掉 12.60、PES 掉 2.60，均值掉 7.60——所有消融里影响最大的单项。

机制 3 · 思想掩码

互动格式是 [内心想法] 说的话 (做的动作)。当角色 A 看历史时，只有 A 自己参与的互动能看到 [...] 里的内心独白；别人参与的互动，方括号内容被正则剥掉。

# simulation/utils.py:58
def remove_other_character_thoughts(text):
    return re.sub(r"\[.*?\]", "", text, flags=re.S).strip()

这保证了信息不对称——演员不能"读心"，必须靠对方说出口的话和做出来的动作来推断。

容易被忽略的实现细节

段切分（Segment Split）

一旦 world_update 真的改了状态，上下文立刻重置：

# simulator.py:1037
if world_update.get("update_global") or world_update.get("update_location"):
    seg_start_idx = len(scene_record["interactions"])
    nc_messages = _build_nc_context()   # 重建 system prompt
    ig_contexts.clear()                  # 清空多轮上下文

因为训练数据也是这样切的（transform.py 的 build_world_state_segments）。推理时必须复现训练时的上下文切分方式，否则模型看到的历史结构和训练时不一致，行为会崩。这是整个项目最容易踩坑的地方。

特殊演员

  • Environment：环境本身作为行动者，生成氛围、天气、人群反应、物理变化。不抢角色的台词和内心。
  • 角色组：多个角色作为一个整体行动（"一家人一起进门"）。生成的是一个共享的瞬间，不是轮流发言。

04持久状态

就是一个 Python dict。没有数据库、没有向量库、没有图结构。

运行时

# simulator.py:435-444
state = {
    "book_name": "A Doll's House",
    "source_scene_index": 19,
    "world_state": snapshot["world_state"],              # 世界状态
    "character_states": snapshot["character_states"],  # 所有角色状态
    "scene_history": [],                                # 已完成的场景
    "previous_scene_context": snapshot.get("previous_scene"),
    "story_finished": False,
    "stop_reason": None,
}

每场结束，world_state 和 character_states 被原地更新，scene_history 追加一条。

角色状态：4 个字符串

{
  "Nora": {
    "profile": "**Social Standing**\nWife of a newly appointed bank manager...\n\n**Core Personality**\n...",
    "short_description": "Nora is the wife of Torvald Helmer... (50-80 词)",
    "motivation": "She is determined to keep Torvald from reading the letter... (1-3 句)",
    "hidden_tracker": "Accumulated pressure from Krogstad's blackmail... (<300 词)"
  }
}
字段类型长度约束作用
profileMarkdown 字符串无硬限制开放式档案，维度因书而异
short_description字符串50–80 词给 scene_cast 选人用
motivation字符串1–3 句本场动机，每场重生成
hidden_tracker字符串<300 词弱信号累积，每次覆盖

为什么 profile 是 Markdown 而不是 JSON？开放式 schema 下维度是模型自己定的，用 JSON 会逼它套固定键。代码里做了兜底：模型返回 dict 时用 dict_to_markdown_text() 转回 Markdown（simulator.py:1079）。

世界状态：全局是字符串，地点是 dict

{
  "global_state": "**Social Order & Class**\n19th-century bourgeois society...\n\n**Marriage & Family**\nHusband is provider...",
  "location_states": {
    "The Helmer Apartment": {
      "Detailed Description": "The remnants of festivities remain...",
      "Important Entities": [
        {"name": "Letter-box", "state": "contains Krogstad's letter, locked"},
        {"name": "Christmas tree", "state": "stripped, candles burnt down"}
      ]
    }
  },
  "location_descriptions": {
    "The Helmer Apartment": "A comfortable middle-class apartment in late 19th-century Norway."
  }
}
字段类型说明
global_stateMarkdown 字符串开放式维度，自由散文
location_statesdict需要实体级追踪，必须结构化
location_descriptionsdict[str, str]静态高层描述，仿真中不变

为什么类型不一样？

全局状态是"社会秩序、历史背景、文化价值观"这类抽象维度，用散文表达最自然；地点状态要追踪"信箱里有没有信""圣诞树烧没烧完"这种具体实体的具体状态，必须能逐条增删改。

代码里对两者做了不同的类型兜底（simulator.py:1125-1141）：global_state 如果是 dict → 转 Markdown；location_state 如果是 str → 尝试 json.loads 转回 dict。

地点卡的两种合法结构

_validate_location_card（main.py:3474）强制二选一，靠有没有 Sub Locations 键来区分。

地点没有重要子区域时使用。

{
  "Detailed Description": "Concise, vivid description...",
  "Important Entities": [
    {"name": "entity name", "state": "initial condition / position"}
  ]
}

地点明显包含子区域时使用（如"庄园"含"卧室""花园"）。

{
  "Detailed Description": "Overall description and how sub-locations relate...",
  "Sub Locations": [
    {
      "name": "sub-location name",
      "description": "what it is like and how it functions",
      "Important Entities": [{"name": "...", "state": "..."}]
    }
  ]
}

校验规则很硬：Important Entities 里每项必须有 name 和 state，且绝不能包含人物（人物档案单独维护）。

历史格式：带坐标的追加列表

历史坐标含义
global_card_history第几场、第几轮互动之后改的
location_cards[name]同上，按地点分开
profile_history第几场之后改的（无 interaction_index）

初始条目用哨兵值：interaction_index: -1 表示"故事开始前"，scene_index: -1 表示初始地点描述。

这个坐标系统是评测的基础——data_loader.py 靠它精确还原"第 k 场开始时世界是什么样"：场景开始 = 最后一个 scene_index < k 的条目；场景结束 = 最后一个 scene_index == k 的条目，没有就回退到开始。

一句话总结

持久状态 = 一个 Python dict，装着「全局状态（Markdown 散文）+ 每个地点的状态（结构化 JSON，含实体列表）+ 每个角色的 4 个字符串」。每轮互动后 dump 成 3 个 JSON，历史用 (scene_index, interaction_index) 坐标索引。

书的分割

57 本书
├── 10%  → OOD 测试书（不参与训练，快照从后 70% 场景采样，最多 20 个）
└── 90%
    ├── 一半 → train+test 书（前 70% 场景训练，后 30% 出 ID 测试点，最多 5 个）
    └── 一半 → train-only 书（全部场景训练）

分割结果存到 dataset/book_split.json。

7 个任务的数据怎么切出来

  • 段切分：build_world_state_segments 在每个世界状态变化点切开，保证每段内世界状态恒定
  • 多轮样本按"演员元组"展开：一个 segment 里每个不同的 actor 组合各生成一条样本，该组合的回合作 assistant、其余作 human，连续同角色合并以维持严格交替
  • world_update 负采样 1:1 动态配平：先数正例，再令 neg_rate = min(1.0, n_pos/n_neg)，而不是固定 5%
  • ShareGPT 格式校验：system → human → 严格交替 → assistant 结尾，不通过会打警告

仓库默认 --max-scenes 5、--max-turns-per-scene 12；论文用的是 20 场景 / 50 互动。要复现论文数字必须显式传 --max-scenes 20 --max-turns-per-scene 50。而且论文的核心卖点恰恰是"长程不衰减"，用默认的 5 场景根本测不出来。

健壮性设计

  • 重复检测：_looks_repetitive_interaction / _looks_self_repetitive_interaction 检测近重复和自循环，命中就带"反重复提醒"重试一次
  • JSON 修复：extract_json_fragment() 能修截断的 JSON；解析失败最多重试 5 次，重试时 temperature 抬到 0.8
  • 实时落盘：每轮互动后写 meta.json / all_scenes.json，进程崩了也有部分结果
  • Prompt 多样性：每个快照随机抽一套风格（natural 40% / = 30% / # 20% / * 10%）+ 5 个 role 变体 + 5 个 task 变体，整个快照内固定

打分机制

基础分 50
judge 先列 merits（每项 +1 ~ +10）
再列 demerits（每项 −1 ~ −10）
最终 = min(100, max(0, 50 + Σmerits − Σdemerits))

judge.py:229 的 _recalculate_score() 会忽略模型自己报的分数，只用 merits/demerits 重算——防止 judge 自评不一致。

总分：CHARACTER_score = 11 项算术平均，WORLD_score = 9 项算术平均；任何一项缺失就返回 None，而不是静默记 50。

两种错误惩罚

IC 惩罚

penalty = min(50, 50 / ln(n+1))

n = 失败前该模型的调用次数。首次调用就失败 → 罚满 50，IC 归零；成功几百次后失败 → 仍罚约 8–10 分。

Metric 惩罚

score = score × N / (N+1)

等价于追加一个 0 分场景。N = 已成功完成的场景数。N=0 时直接置 0。

任务到指标的映射见论文 Table 9：scene_cast→CSR,SCC；location_scenario→LSR,SCC；next_character→TSO；world_update→GUS,GSA,LUS,LSA；interaction_gen→PF,SSF,MDB,EA,EU,CR,NP；character_update→PUF,PES；motivation_update→MQ。

成本

一个 20 场景、5 角色的样本约 142 次串行 judge 调用：

  • 18 个 per-scene 指标 × 7 场景 = 126 次
  • PAIRED_METRICS 把 4 对指标合并成单次调用（PF+SSF、EA+EU、GUS+GSA、LUS+LSA），省掉约 28 次
  • 加 N 次场景摘要（无条件生成）+ C 个角色的 PES + 1 次 SCC

样本内完全串行，并发只在样本之间（ProcessPoolExecutor）。

人工验证

60 条轨迹、3 组模型对、每组 3 名母语标注者、共 180 条标注，每条约 1 小时。人机一致率 85%~100%，维度级 81.7%~100%。

09发现的问题

读代码时发现的 bug 和文档不一致，按影响排序。

最该修的三条

① hidden_tracker 时间错位

data_loader.py:714-722 取的是场景结束后的 tracker，但 prompts.py:1183 贴的标签是 "## Character Hidden Trackers (at scene start)"。

影响：PF / SSF / MDB 三个指标看到的是被评判场景的结果，等于给 judge 泄露答案，会系统性抬高分数。也会影响论文 Table 15 那个 hidden tracker 消融的可信度。

② 场景采样不可复现

main.py:384 用未播种的全局 random.sample；--sample_seed 只影响 --sample_ratio 的样本选择。

影响：同一 sample 重跑，每个指标抽到的 7 个场景不同，分数就不同。--resume 能跳过已完成样本，但无法复现已有分数。

③ lang_detect 对中文书永远失效

world_initialization（main.py:3185）和 world_dynamic（main.py:3679）读 scenes[0]['text']，但 text 字段在上游 standardize_location_names 里已被 remove_private_scene_fields() 弹掉。

影响：lang_detect('') 恒返回 'en'，中文书的世界卡会被要求用英文生成。

其他问题

数据构建侧
  • restore_from_cache 是死代码——extract 刚写完文件它就检查"文件存在则跳过"，恒真；即使 --regenerate 绕过，缓存过滤器还要求 model == 'claude-3-5-sonnet-20240620' 和一段已不存在的 prompt 前缀
  • 靠函数名耦合——get_response_json 用 post_processing_func.__name__ == 'parse_response' 判断是否走备份重试，任何重命名都会静默关掉整条链路
  • 13 个阶段里 11 个吞异常——失败时 return book['title']，process_book 只检查最后一个返回值，中间失败也会打印 "Successfully processed"
  • 缓存键把整本书塞进去了——cached 用 str(args)+str(kwargs.items()) 做键，每次 miss 重写整个 pickle，开销随缓存增长呈平方级
  • 训练侧 prompt 风格被写死——build_diverse_task_prompt 硬编码 style='plain'，set_book_prompt_style() 全仓库无调用点，=/#/* 三种标题装饰在数据构建侧不可达
  • 硬编码模型名——utils.py:1187/1199 把 claude-3-5-sonnet-2.0 写死用于 JSON 修复/拒答改写，无视 --model
  • split.py 的 JSON 修复路径会崩——extract_json(response) 在 4 处调用时都没传 model=，走到 LLM 修复分支就 KeyError
评测侧
  • 全有或全无——compute_final_scores 里 11 项任何一项为 None，总分就是 None。~140 次调用里一次重试耗尽，整个样本就从均值里消失
  • 打分解析脆弱——judge.py:249 的 abs(m["points"]) 遇到字符串或 None 抛 TypeError，异常冒到样本级 except，整个样本失败

  • IC 惩罚的 n 是估算不是计数——data_loader.py:371-438 从场景结构反推，trace.json 里有真实记录却没用。论文原文说的是"total number of calls"

  • 指标清单重复定义——aggregator.py:22-31 和 prompts.py:1460-1466 各一份，改一处漏一处
